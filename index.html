📋 OVERVIEW

Entra Agent ID — Concepts & Architecture

▶

Microsoft Entra Agent ID introduces a new identity model for AI agents. It allows organizations to create, manage, and govern AI agent identities with the same rigor applied to human identities. There are three key identity primitives:

Identity Hierarchy & Token Flow

🔷 Agent Blueprint A special application registration (AgentIdentityBlueprint) that defines the template. One blueprint can have multiple agent identities.
🟢 Agent Identity A service principal linked to a blueprint. Used for Autonomous Agent scenarios — the agent operates under its own security context.
🟡 Agentic User (Digital Colleague) A special User object with email, Teams, OneDrive. The AI agent acts as a Digital Colleague with its own M365 identity.
🔴 On-Behalf-Of User The AI agent acts on behalf of a human user, carrying the user's security context via OAuth 2.0 authorization code flow.
🟣 Third-Party Sidecar A containerized Auth SDK sidecar runs alongside third-party agents (AWS Bedrock, Ollama, n8n). The agent requests tokens from the sidecar, never handling credentials directly.

Authentication Scenarios

Scenario Identity Used Token Flow Steps
Autonomous Agent Agent Identity FIC → Client Credentials 05.01 → 05.02
Digital Colleague Agentic User FIC → FIC → user_fic 04.01 → 04.02 → 04.03
On-Behalf-Of Human User via AI App Auth Code + PKCE 06.01
Third-Party Sidecar Agent Identity via Sidecar Sidecar → Entra Agent ID → Token 07.01 → 07.02 → 07.03
🔑
How auth works in this demo: Steps 01, 02, 03 use your signed-in user's delegated token (MSAL.js interactive) with the Agent ID Administrator role. Steps 04–05 use the Blueprint's credentials for FIC token chains. Note: in production, step 02 would use the Blueprint's own client_credentials, but browsers block that due to CORS.

01.01

Create the Agent Identity Blueprint

🔑 Delegated ▶

The Agent Identity Blueprint is a special type of application registration (@odata.type: Microsoft.Graph.AgentIdentityBlueprint). It serves as the template for creating Agent Identities — think of it as the "class" from which agent "instances" are derived. A sponsor is required to establish organizational accountability. A sponsor can be an individual user (by UPN) or a security group — enabling clear ownership and governance of the agent.

ℹ️
This call uses your signed-in delegated token. The @odata.type field tells Microsoft Graph to create an AgentIdentityBlueprint rather than a regular application.
POST https://graph.microsoft.com/beta/applications/
{ "@odata.type": "Microsoft.Graph.AgentIdentityBlueprint", "displayName": "[ai] Blueprint for Digital Worker 01", "sponsors@odata.bind": [ "https://graph.microsoft.com/v1.0/{{users|groups}}/{{sponsorId}}" ] }
📋 Parameters Explained
  • @odata.type — Tells Graph this is an AgentIdentityBlueprint, not a regular app registration
  • displayName — Human-readable name for the blueprint
  • sponsors@odata.bind — OData bind to a user or security group that acts as the organizational sponsor/owner of the agent

01.02

Create the Agent Blueprint Service Principal

🔑 Delegated ▶

Every application registration needs a corresponding Service Principal in the tenant. For the Agent Blueprint, we create a special agentIdentityBlueprintPrincipal using a dedicated Graph endpoint. This is what enables the blueprint to authenticate and create agent identities.

POST https://graph.microsoft.com/beta/serviceprincipals/graph.agentIdentityBlueprintPrincipal
{ "appId": "{{blueprintAppId}}" // from step 01.01 }
📋 Parameters Explained
  • appId — The Application (client) ID of the blueprint created in step 01.01
  • The endpoint graph.agentIdentityBlueprintPrincipal is an OData cast that creates an agent-specific service principal type

01.03

Authenticate the Blueprint (Secret or Managed Identity)

🔑 Delegated ▶

The Blueprint needs its own credential so it can act as itself (not as a user). This is needed because:

  • Creating Agent Identities (step 02) — the Agent Identity must be created by its parent Blueprint using client_credentials, not by a user. This parent–child binding is how Entra links each identity back to its blueprint.
  • Federated Identity Credential (FIC) token chain (steps 04–05) — the Blueprint's credential is the starting point of the token chain that lets an AI application eventually obtain tokens on behalf of the Agent User.
  • Autonomous Agent scenario — the Blueprint authenticates itself to get a Graph token for the Agent Identity to act independently (no user present).

Choose one of the two options below. A client secret is fine for demos; for production, use a Managed Identity with a Federated Identity Credential (FIC).

⚠️
Demo/PoC only! Client secrets are easy to set up but should not be used in production — they can be leaked and have a fixed expiry. Wait ~30 seconds after this step for replication.
POST https://graph.microsoft.com/beta/applications/{{blueprintObjectId}}/addPassword
{ "passwordCredential": { "displayName": "Demo Secret", "endDateTime": "2027-08-05T23:59:59Z" } }
🛡️
Production recommended. Instead of a secret, you configure a Federated Identity Credential (FIC) on the Blueprint that trusts a Managed Identity from your Azure resource (e.g. Azure VM, App Service, Azure Function). The Managed Identity gets a token from Azure AD, and the Blueprint trusts it via the FIC — no secrets to rotate or leak.
POST https://graph.microsoft.com/beta/applications/{{blueprintObjectId}}/federatedIdentityCredentials
{ "name": "ManagedIdentityFIC", "issuer": "https://login.microsoftonline.com/{{tenantId}}/v2.0", "subject": "{{managedIdentityObjectId}}", "audiences": ["api://AzureADTokenExchange"] }
📋 Parameters Explained
  • name — A unique name for this federated credential
  • issuer — The Entra ID token issuer URL for your tenant
  • subject — The Object ID of your Azure Managed Identity (User-Assigned or System-Assigned)
  • audiences — Must be api://AzureADTokenExchange for Azure-to-Azure FIC scenarios
Find this in the Azure Portal → your Managed Identity resource → Overview → Object (principal) ID

01.04

Expose API Scope for the Blueprint

🔑 Delegated ▶

Expose an OAuth 2.0 permission scope (access_agent) on the Agent Blueprint. This is needed for the On-Behalf-Of scenario (step 06) where an end user delegates access to the AI Agent through the blueprint.

PATCH https://graph.microsoft.com/beta/applications/{{blueprintObjectId}}
{ "identifierUris": ["api://{{blueprintAppId}}"], "api": { "oauth2PermissionScopes": [{ "adminConsentDescription": "Allow the application to access the agent on behalf of the signed-in user.", "adminConsentDisplayName": "Access agent", "id": "{{auto-generated-guid}}", "isEnabled": true, "type": "User", "value": "access_agent" }] } }
📋 Parameters Explained
  • identifierUris — Sets the App ID URI (api://<appId>)
  • oauth2PermissionScopes — Defines a delegated permission scope for consent
  • value — The scope string: api://<appId>/access_agent

02.01

Create the Agent Identity

🔑 Delegated ▶

The Agent Identity is a special service principal linked to the Agent Blueprint. It represents the agent's own identity in the directory. An Agent Blueprint can have multiple Agent Identities, but each identity belongs to exactly one blueprint. This identity is used for Autonomous Agent scenarios.

🔑
This step uses your delegated token with the Agent ID Administrator role. In production, the Agent Identity would be created by the Blueprint's own credentials (client_credentials), but that flow is blocked by CORS in browsers. The result is identical — the Agent Identity is linked to the Blueprint via agentAppId.
POST https://graph.microsoft.com/beta/serviceprincipals/Microsoft.Graph.AgentIdentity
{ "displayName": "[ai] Agent Identity for Digital Worker 01", "agentAppId": "{{blueprintAppId}}", "sponsors@odata.bind": [ "https://graph.microsoft.com/v1.0/{{users|groups}}/{{sponsorId}}" ] } // Auth: client_credentials token from Blueprint app (not user delegated)
📋 Parameters Explained
  • agentAppId — Links this identity to the parent Agent Blueprint
  • sponsors@odata.bind — Same sponsor (user or group) for governance
  • Microsoft.Graph.AgentIdentity — OData cast for creating this special service principal type

Create the Agentic User (Digital Colleague)

🔑 Delegated ▶

The Agentic User (Digital Colleague) is a special User of type microsoft.graph.agentUser. Unlike a regular user, this digital worker has its own email, Teams presence, OneDrive, and calendar — but is driven by AI. The identityParentId links it to the Agent Identity from step 02.

POST https://graph.microsoft.com/beta/users
{ "@odata.type": "microsoft.graph.agentUser", "displayName": "[ai] Digital Worker 01 Agent User", "userPrincipalName": "{{agentUserUpn}}", "mailNickname": "{{agentUserMailNick}}", "accountEnabled": true, "identityParentId": "{{agentIdentityId}}" }

03.02

Grant Permissions for the Agentic User

🔑 Delegated ▶

By least privilege, an Agentic User has zero permissions by default. You must explicitly create an oauth2PermissionGrant so the Agent Identity can access Graph APIs on behalf of the Agentic User.

API Call

04

Digital Colleague Auth — 3-Hop FIC Token Chain

▶

Token Flow: Blueprint → Agent Identity → Agentic User → MS Graph

04.01

Obtain Blueprint FIC Token (Digital Colleague)

🔐 Blueprint Credentials ▶

The Digital Colleague auth involves a chain of Federated Identity Credential (FIC) tokens. First, the Agent Blueprint authenticates with its own credentials and requests a FIC token scoped to api://AzureADTokenExchange. The fmi_path parameter is a Microsoft-specific extension pointing to the target Agent Identity.

🔗
What is FIC and why is it needed here?
A Federated Identity Credential (FIC) establishes a trust relationship between two identities without sharing secrets. Instead of the Agent Identity having its own client secret, it trusts tokens issued by the Blueprint. This is how Entra enforces the parent–child relationship: only the Blueprint can create tokens that the Agent Identity will accept.

The token chain works like this: Blueprint credential → FIC token (intermediate) → Agent Identity token → final Graph token. Each hop proves trust without exposing secrets between entities. This is the same concept used by Managed Identities and GitHub Actions OIDC — one identity vouches for another.
🔑
fmi_path is a custom OAuth extension. It tells Entra to issue a Federated Identity Credential token that can be exchanged for an Agent Identity token in the next step.
POST https://login.microsoftonline.com/{{tenantId}}/oauth2/v2.0/token
// Authorization: Basic base64(blueprintAppId:blueprintSecret) scope = api://AzureADTokenExchange/.default grant_type = client_credentials fmi_path = {{agentIdentityId}} // custom extension
💡
The client_credentials flow is blocked by CORS in browsers. Click the button to generate a PowerShell command, run it in a terminal, then paste the JSON response back.

          04.02
          
Obtain Agent Identity FIC Token

          🔐 FIC Chain
          ▶
        

        

          

            Using the Blueprint FIC token from step 04.01, request a second FIC token for the Agent Identity.
            The client_assertion carries the Blueprint FIC token as a JWT bearer assertion, proving the trust chain:
            Blueprint → Agent Identity.
          

          

            🔗
            

              Why a second FIC hop? The Blueprint FIC token from step 04.01 proves "I am the Blueprint and I vouch for this Agent Identity". This step exchanges that proof for a token scoped to the Agent Identity itself. This two-hop pattern ensures that neither the AI application nor the Blueprint can directly impersonate the Agent Identity — both hops must succeed, enforcing the governance chain.
            

          


          

            

              POST
              https://login.microsoftonline.com/{{tenantId}}/oauth2/v2.0/token
            

            
client_id              = {{agentIdentityId}}
scope                  = api://AzureADTokenExchange/.default
grant_type             = client_credentials
client_assertion_type  = urn:ietf:params:oauth:client-assertion-type:jwt-bearer
client_assertion       = {{blueprintFicToken}}  // from step 04.01

          04.03
          
Obtain Agent User Token (Digital Colleague)

          🔐 FIC Chain
          ▶
        

        

          

            Final step in the Digital Colleague auth chain. Using both FIC tokens (Blueprint + Agent Identity),
            request an MS Graph access token for the Agentic User. The custom grant_type=user_fic
            with requested_token_use=on_behalf_of issues a token representing the Digital Colleague.
          

          

            🔗
            

              The complete FIC chain: This is the culmination of the 3-hop trust chain. The client_assertion (Blueprint FIC token) proves the Blueprint's identity, while user_federated_identity_credential (Agent Identity FIC token) proves the Agent Identity's identity. Together, they authorize Entra to issue a token for the Agentic User — a real M365 user object the agent can act as. The user_fic grant type is specific to this Digital Colleague scenario and is not used in standard OAuth flows.
            

          

          

            ✅
            
The resulting token lets you call MS Graph as the Digital Colleague — with its own email, Teams, calendar, etc.

          


          

            

              POST
              https://login.microsoftonline.com/{{tenantId}}/oauth2/v2.0/token
            

            
client_id                           = {{agentIdentityId}}
client_assertion_type              = urn:ietf:params:oauth:client-assertion-type:jwt-bearer
client_assertion                   = {{blueprintFicToken}}
grant_type                         = user_fic           // custom grant type
requested_token_use                = on_behalf_of
scope                              = https://graph.microsoft.com/.default
username                           = {{agentUserUpn}}
user_federated_identity_credential = {{agentIdentityFicToken}}

          05.01
          
Obtain Blueprint FIC Token (Autonomous Agent)

          🔐 Blueprint Credentials
          ▶
        

        

          

            For the Autonomous Agent scenario, the Agent Identity operates under its own security context —
            no human user involved. First step: obtain a Blueprint FIC token (identical to 04.01).
          

          

            🔗
            

              Autonomous vs. Digital Colleague — when to use which?

              • Digital Colleague (section 04): The agent has its own M365 identity — email, Teams, calendar. Use when the agent needs to interact as a "person" in the organization (e.g., a virtual assistant that sends emails, joins meetings, chats on Teams). Requires an Agentic User (step 03) and a 3-hop FIC chain.

              • Autonomous Agent (this section): The agent acts under the Agent Identity's service principal — no user identity needed. Use for backend/API agents that process data, call APIs, or perform automated tasks without needing a user mailbox or Teams presence. Only requires a 2-hop FIC chain (Blueprint → Agent Identity → Graph).


              Both scenarios start the same way — with a Blueprint FIC token — but diverge at the next step.

          05.02
          
Obtain Agent Identity MS Graph Token

          🔐 FIC Chain
          ▶
        

        

          

            Using the Blueprint FIC token, request an MS Graph access token for the Agent Identity.
            Unlike Digital Colleague (which uses user_fic), the Autonomous Agent uses standard
            client_credentials with a JWT bearer assertion.
          

          

            🔗
            

              Why is this simpler than Digital Colleague? The Autonomous Agent only needs 2 hops: Blueprint FIC → Agent Identity Graph token. There's no Agentic User involved, so no user_fic grant type or third token exchange. The Agent Identity authenticates directly as a service principal. The permissions it gets are the application permissions granted to it via admin consent (step 03.02), not delegated user permissions.
            

          

          

            ✅
            
This token represents the Autonomous Agent — it can access any Graph resources the Agent Identity has application permissions for.

          07.03
          
Request Token via Sidecar

          🐳 Container
          ▶
        

        

          

            Once the sidecar is running, your agent requests tokens by calling the sidecar's /token endpoint.
            The sidecar handles all credential management and returns a standard OAuth 2.0 access token.
            This is how your third-party agent (AWS Bedrock, Ollama, n8n, etc.) gets tokens without ever seeing credentials.
          


          
Token Request Flow

          

            1
            Agent sends a GET to http://sidecar:5000/AuthorizationHeaderUnauthenticated/graph-app — the downstream API name is a path segment, not a query parameter.
            2
            Sidecar authenticates with Entra Agent ID using the Blueprint's client credentials + Agent Identity FIC.
            3
            Sidecar returns the access token to the agent. The agent uses it to call Microsoft Graph or your custom APIs.
          


          

            

              
              
              The downstream API name configured in the sidecar environment (e.g. graph-app for autonomous, graph for OBO).
            

          


          

            
          


          

            

              

                GET
                http://sidecar:5000/AuthorizationHeaderUnauthenticated/graph-app
                
              

              

            


            

              📋
              
Run the command above in your terminal (where the Docker Compose stack is running). Paste the JSON response below to verify the token.

import requests

SIDECAR_URL = "http://sidecar:5000"

def get_graph_token():
    resp = requests.get(
        f"{SIDECAR_URL}/AuthorizationHeaderUnauthenticated/graph-app"
    )
    resp.raise_for_status()
    return resp.json()["authorizationHeader"]

auth_header = get_graph_token()
auth_header = get_graph_token()
# Decode the JWT to inspect its claims
import base64, json
payload = auth_header.split(".")[1] + "=="
claims = json.loads(base64.urlsafe_b64decode(payload))
print(json.dumps(claims, indent=2))

const SIDECAR_URL = "http://sidecar:5000";

async function getGraphAuthHeader() {
  const resp = await fetch(
    `${SIDECAR_URL}/AuthorizationHeaderUnauthenticated/graph-app`
  );
  const data = await resp.json();
  return data.authorizationHeader;  // "Bearer eyJ0eX..."
}

const authHeader = await getGraphAuthHeader();
// Decode the JWT to inspect its claims
const payload = authHeader.split(".")[1];
const claims = JSON.parse(atob(payload.replace(/-/g,"+").replace(/_/g,"/")));
console.log(claims);

Audit Agent Blueprints — Missing Sponsors

          🔑 Delegated
          ▶
        

        

          

            Lists all Agent Identity Blueprints in your tenant and checks which ones are missing sponsors.
            Blueprints without sponsors lack organizational accountability — a key governance requirement.
            Results can be downloaded as CSV for reporting.
          

          

            ⚠️
            
This audit may take a moment if your tenant has many blueprints. Each blueprint's sponsors are checked individually. The scan handles pagination automatically.

          


          

            

              GET
              https://graph.microsoft.com/beta/applications/microsoft.graph.agentIdentityBlueprint?$select=id,appId,displayName,createdDateTime
            

            
// For each blueprint, checks sponsors via:
// GET /beta/applications/{id}/microsoft.graph.agentIdentityBlueprint/sponsors?$select=id,displayName

          


          

            
            
          


          
          

            
🔧 Quick Fix: Assign Sponsor to Flagged Blueprints

            
Enter a sponsor (user UPN or security group name) to assign to all blueprints flagged as Missing Sponsors.

            

              💡
              
This flow supports bulk updates — if multiple blueprints are missing sponsors, all of them will be updated in a single operation. The same sponsor is assigned to every flagged blueprint using throttled concurrent API calls. Preview the API call first to verify before executing.

          08.03
          
Continuous Monitoring — KQL Alert Rule

          ▶
        

        

          

            Steps 08.01 and 08.02 provide point-in-time audits. For continuous monitoring, you can configure
            Azure Monitor alert rules using KQL queries against your Entra ID Audit Logs in Log Analytics.
            This ensures you get notified whenever an Agent Blueprint or Agent Identity is created without a sponsor.
          


          

            📋
            
Prerequisites: You need an Entra ID tenant with Diagnostic Settings configured to send
            Audit Logs to a Log Analytics workspace. Go to Entra ID → Diagnostic settings → Add diagnostic setting and enable AuditLogs.

          


          
KQL — Detect Blueprints Created Without Sponsors

          

            This query detects Add application audit events where the application type is AgentIdentityBlueprint
            but no sponsors binding was included in the creation payload.
          

          

            

              KQL
              Blueprints without sponsors
              
            

            
AuditLogs
| where TimeGenerated > ago(24h)
| where OperationName == "Add application"
| where Result == "success"
// Look for AgentIdentityBlueprint in the modified properties
| mv-expand TargetResource = TargetResources
| where TargetResource.type == "Application"
| mv-expand ModifiedProperty = TargetResource.modifiedProperties
| where ModifiedProperty.displayName == "@odata.type"
    and ModifiedProperty.newValue has "AgentIdentityBlueprint"
// Check if sponsors binding is absent
| where not(TargetResources has "sponsors")
| project
    TimeGenerated,
    OperationName,
    BlueprintName = tostring(TargetResource.displayName),
    BlueprintId = tostring(TargetResource.id),
    InitiatedBy = coalesce(
        tostring(InitiatedBy.user.userPrincipalName),
        tostring(InitiatedBy.app.displayName),
        "Unknown"
    ),
    CorrelationId
| order by TimeGenerated desc

          


          
KQL — Detect Agent Identities Created Without Sponsors

          

            This query detects Add service principal events for Agent Identity types that were created without a sponsor binding.
          

          

            

              KQL
              Agent Identities without sponsors
              
            

            
AuditLogs
| where TimeGenerated > ago(24h)
| where OperationName == "Add service principal"
| where Result == "success"
| mv-expand TargetResource = TargetResources
| where TargetResource.type == "ServicePrincipal"
| mv-expand ModifiedProperty = TargetResource.modifiedProperties
| where ModifiedProperty.displayName == "ServicePrincipalType"
    or ModifiedProperty.displayName == "@odata.type"
| where ModifiedProperty.newValue has_any (
    "AgentIdentity", "agentIdentity", "agentIdentityBlueprintPrincipal"
)
// Check if sponsors binding is absent
| where not(TargetResources has "sponsors")
| project
    TimeGenerated,
    OperationName,
    IdentityName = tostring(TargetResource.displayName),
    IdentityId = tostring(TargetResource.id),
    AppId = tostring(TargetResource.appId),
    InitiatedBy = coalesce(
        tostring(InitiatedBy.user.userPrincipalName),
        tostring(InitiatedBy.app.displayName),
        "Unknown"
    ),
    CorrelationId
| order by TimeGenerated desc

          


          
KQL — Combined Alert (Blueprints + Identities)

          

            A single unified query that covers both blueprints and agent identities. Use this for a single alert rule
            that catches any agent-related object created without a sponsor.
          

          

            

              KQL
              Combined alert — all agent objects
              
            

            
let BlueprintsWithoutSponsors = AuditLogs
| where TimeGenerated > ago(24h)
| where OperationName == "Add application"
| where Result == "success"
| mv-expand TargetResource = TargetResources
| where TargetResource.type == "Application"
| mv-expand ModifiedProperty = TargetResource.modifiedProperties
| where ModifiedProperty.displayName == "@odata.type"
    and ModifiedProperty.newValue has "AgentIdentityBlueprint"
| where not(TargetResources has "sponsors")
| project
    TimeGenerated,
    ObjectType = "AgentIdentityBlueprint",
    ObjectName = tostring(TargetResource.displayName),
    ObjectId = tostring(TargetResource.id),
    InitiatedBy = coalesce(
        tostring(InitiatedBy.user.userPrincipalName),
        tostring(InitiatedBy.app.displayName),
        "Unknown"
    ),
    CorrelationId;
let IdentitiesWithoutSponsors = AuditLogs
| where TimeGenerated > ago(24h)
| where OperationName == "Add service principal"
| where Result == "success"
| mv-expand TargetResource = TargetResources
| where TargetResource.type == "ServicePrincipal"
| mv-expand ModifiedProperty = TargetResource.modifiedProperties
| where ModifiedProperty.displayName in (
    "ServicePrincipalType", "@odata.type"
)
| where ModifiedProperty.newValue has_any (
    "AgentIdentity", "agentIdentity",
    "agentIdentityBlueprintPrincipal"
)
| where not(TargetResources has "sponsors")
| project
    TimeGenerated,
    ObjectType = "AgentIdentity",
    ObjectName = tostring(TargetResource.displayName),
    ObjectId = tostring(TargetResource.id),
    InitiatedBy = coalesce(
        tostring(InitiatedBy.user.userPrincipalName),
        tostring(InitiatedBy.app.displayName),
        "Unknown"
    ),
    CorrelationId;
union BlueprintsWithoutSponsors, IdentitiesWithoutSponsors
| order by TimeGenerated desc

          


          
How to Set Up the Alert Rule

          

            
    
              
  1. Go to Azure Portal → Monitor → Alerts → Create alert rule
    2. 
              
  2. Set Scope to your Log Analytics workspace that receives Entra ID audit logs
    3. 
              
  3. Under Condition, choose Custom log search and paste the combined KQL query above
    4. 
              
  4. Set Measure to Table rows, Aggregation type to Count, Threshold to greater than 0
    5. 
              
  5. Set Evaluation frequency (e.g. every 1 hour) and Lookback period (e.g. 1 hour) to match
    6. 
              
  6. Under Actions, select or create an Action Group (email, Teams webhook, Logic App, etc.)
    7. 
              
  7. Set Severity (e.g. Sev 2 — Warning) and a descriptive alert rule name
    8. 
              
  8. Click Create — you'll now be alerted when ungoverned agent objects appear in your tenant
    9. 
            

          


          

            ⚠️
            
Audit log delay: Entra ID audit logs may have a latency of 5–15 minutes before they appear in Log Analytics. Factor this into your alert evaluation frequency. A 1-hour evaluation window provides reliable coverage.

          


          

            💡
            
Tip: Combine this alert with the Quick Fix workflow from steps 08.01/08.02. When you receive an alert, open this demo, run the audit, and use the bulk sponsor assignment to remediate immediately.
